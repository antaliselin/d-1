## 0　摘要

**这段要回答**：这个系统在整局里负责什么，不负责什么，谁依赖它。

### 0.1　一句话职责

负责生成客人：**包括来几位客人、容器规格、物品需求、预算、生命值、以及对话与事件链**，把结果组装成一个 `CustomerInstance` 交给其它系统。同时持有**声望**。

### 0.2　不做什么

| 不做                           | 谁做           |
| ------------------------------ | -------------- |
| 不判断物品能不能放进容器       | S01 网格与容器 |
| 不管库存、实例、归属           | S02 物品与库存 |
| 不算这件货值多少钱             | S05 结算       |
| 不处理拖拽手势                 | S03 拖拽与交互 |
| 不管哪天开门、什么时候叫下一位 | 状态机 / 日程  |
| 不画立绘、不做气泡             | 客户端表现     |

### 0.3　依赖

- 上游：S02（物品定义，用来抽需求与自带物品）、S01（`placeableCount`，用来算自带物品容量）。
- 下游：S03（立绘是投放目标，对白期间只允许拖医疗用品）、S05（需求权重、预算、治疗对象）。

### 0.4　验收标准

一句话：**每位客人都满足自己的约束——自带物品不占满半箱，点名需要的东西一定塞得进容器。**

可测三条：

1. 任意客人生成后，自带物品占格 ≤ 可用格的 60%（硬红线）。
2. 点名要的物品，四个朝向里至少有一个能塞进这个客人的箱子。（计入不可用格，不计算客人自带物品除非你有算法）
3. 需求至少有一段不是点名。

## 1　数据

**这段要回答**：有哪些字段，类型是什么，谁写谁读。

> 这段数据结构仅供参考
>
> 反正，存在普通客人与特殊客人的区别

### 1.1　三张表 + 一个结构

随机客人和特殊客人**不分成两套结构**，只是数据来源不同：

```text
客人档案表（共用）          生成规则表（只有随机客人）      剧本表（只有特殊客人）
  id / name / title           容器（特殊/正常）→ 破洞 / 预算      对白回合 / 选项 / 交易
  look / palette / thanks     需求段权重 / 自带物品比例       开箱时机 / 自动离场
        │                            │                              │
        └────────────┬───────────────┘                              │
                     ▼                                              │
         随机客人：档案 + 规则生成                                    │
         特殊客人：档案 + 剧本 ──────────────────────────────────────┘
                     │
                     ▼
            运行时结构 CustomerInstance（双方共用）
```

判据：**这个字段是策划逐字写死的，还是按规则算出来的？** 写死的进档案/剧本，算出来的进规则表，产出的都是同一个 `CustomerInstance`。

### 1.2　客人档案 `CharacterDef`

| 字段      | 类型   | 含义                                        | 谁写   |
| --------- | ------ | ------------------------------------------- | ------ |
| `id`      | string | 身份键                                      | 策划表 |
| `name`    | string | 名字                                        | 策划表 |
| `title`   | string | 头衔（显示在名字下面）                      | 策划表 |
| `look`    | enum   | 立绘配件：兜帽/头盔/护目镜/面罩/鸭舌帽/围巾 | 策划表 |
| `palette` | object | 肤色 / 外套 / 点缀色                        | 策划表 |
| `thanks`  | string | 成交后的道谢                                | 策划表 |

> 客人的外观还需要一些技术决策，是利用图片组件超级拼装客人还是固定立绘

身份池当前 6 人。身份只决定"长什么样、叫什么"，**容器、需求、预算、生命值都不属于身份**。

| 字段                      | 类型    | 含义                                   |

## 2　规则

**这段要回答**：算法到底是什么。

### 2.1　今天来几位

一天内来的客人会被声望影响

0~24：20%概率2位客人，80%3位客人 

25~49：70%3位客人，30%4位客人

50~74：50%3位客人，40%4位客人，10%5位客人

75~100：10%3位客人，70%4位客人，20%5位客人

### 2.2　容器

先检查是不是特殊规格的容器

特殊规格容器概率为15%

| 特殊容器名称 | 长度/高度 | 不可用格子数                           | 预算区间 | 自带物品目标占比 |
| ------------ | --------- | -------------------------------------- | -------- | ---------------- |
| 吉他收纳盒   | 8x3       | 0~3                                    | 240~600  | 0~20%            |
| 塑料管道     | 1x10      | 0                                      | 100~200  | 0                |
| 两个手提箱   | 10x6      | 固定位置：第 5/6 竖排全是不可用格子      | 480~960  | 0~10%            |

> 特殊容器的名称仅用于描述长什么样，不参与逻辑

如果没有命中特殊容器，则尝试生成一个正常的容器

正常容器长宽会在 **6~10** 之间独立随机

不可用格子数等于：random（0，长和高里面最低的那个数+2）

预算则会根据容器来调整，取值范围就是 长X高X10 ~ 长X高X20

> 比如说一个10x10的容器，预算就是1000~2000之间随机

尺寸必须落在 `CONTAINER_MIN~MAX`（S01 1.3，6~10）之内，越界直接抛错

**特殊容器不套上面这套公式**：尺寸、不可用格子、预算、自带物品目标占比全部按上表取值，不参与 6~10 的尺寸校验，也不走「长×高×10~20」的预算公式。

### 2.3　需求

```text
需求段数 随机 1 或 2
主段：随机一个类别
次段：类别必须与主段不同
规则：无论几段，都不能全部是点名需求
      → 1 段时不能是点名；2 段时不能两段都是点名
```

三种段类型：

| 类型     | 含义           | 件数                       |
| -------- | -------------- | -------------------------- |
| 类别需求 | "我要子弹"     | 不限件数，按类别算权重     |
| 数量需求 | "至少三件弹药" | `atLeast = 2~4`            |
| 点名需求 | "我要两个金表" | 占格 ≥4 的件数 1；否则 2~3 |

**两道守卫**（生成期就必须过）：

```text
形状守卫：点名要的物品，四个朝向里至少有一个能塞进这个箱子
          （格数够但长度超边长的大件会被换掉）
容量守卫：需求总格数 ≤ 空余可放置格数 × 50%
          超了先把件数降到 1，再超就把该段退化成纯类别需求
```

产出的 `demand` 形如 `[{tags:['ammo'], weight:1}, {tags:['food'], weight:0.6}]`，点名部分进 `wants`。

### 2.4　预算

预算则会根据容器来调整，取值范围就是   长X高X10  ~  长X高X20
见2.2 容器

> 预算目前只由容器决定，与声望无关；后续可能改为声望也参与，届时只改这一节。

预算与需求无关：客人可能带着买不起自己清单的钱来

### 2.5　生命值

首先生命值的合法取值范围是25~100

分为三个区间：

健康 100

受伤 99~50

危险 25~49

50%的客人是健康，25%受伤25%危险



还记得吗？带有heal字段的物品能够拖给客人治疗，然后结算时会检测给客人回复了多少血量来结账

### 2.6　自带物品

```text
目标容量 = round(可用格数 × (0.2~0.5))  // 软目标，允许被最后一件超过
循环：随机取一件物品 → 随机朝向 → 随机落点 → 放得下就放
     达到目标容量就结束循环（最后一件允许把占比顶到目标之上）
     任何一件放进去之前先检查：放完是否超过 60%
       超过 → 不放，撤回并结束循环
       不超过 → 放下
     多次尝试都放不下时，主动寻找 1×1 的物品再试
```

两条硬规则：

- **60% 是不可越过的红线**：任何一次放置都不能让总占格超过可用格的 60%。
- 目标占比（20%~50%）只是"放到这个量级就停"，允许被最后一件超过，但不会超过 60%。

- 自带物品**归客人所有**（`owner = customer`），不计价、不能收回货架。
- 落点由生成器决定，注入动作交给 S01（见 S01 3.3）。

> 特殊容器拥有固定的目标容量，不走0.2~0.5随机

### 2.7　声望涨落

由 S05 在成交后调用，规则：

```text
每类需求都被满足     +1
给客人回满血        +1
物品全部都是需求外      −2
范围始终夹在 0~100
```

- 声望变化不显示数字，只在底部进度条上体现。

### 2.8　特殊客人

特殊客人 = 档案 + 剧本，五点与随机客人不同：

| #   | 特权                   | 说明                                                                             |
| --- | ---------------------- | -------------------------------------------------------------------------------- |
| 1   | **容器可以不放进规则** | 可以没有容器（只能谈生意），也可以延迟上台（`containerHidden`）                  |
| 2   | **数据全部写死**       | 容器尺寸、破洞、自带物品、预算、需求都是表里写的，不走生成                       |
| 3   | **有剧本**             | 对白按回合推进；有选项时必须答完才能成交                                         |
| 4   | **可以做交易**         | 选项可以加钱、扣钱、入库、去货（`effects`）                                      |
| 5   | **不进随机池**         | 随机客人的身份池里没有他们，只能由日程安排出场，抑或是满足条件后取代随机客人出现 |

## 3　状态与流程

**这段要回答**：一个客人从生成到离场经历什么。

### 3.1　一天里的客人

```text
今日名单
  └─ 取第 n 位 → 容器（15% 特殊 / 85% 正常）→ 生成 CustomerInstance（或取剧本客人）
       └─ 进场：立绘 + 气泡 + 容器上台
            ├─ 谈生意：没有容器 → 只有对白与交易
            └─ 装货：容器可交互，玩家放置 / 治疗 / 答选项
                 └─ 成交（S05）→ 道谢 → 离场 → 下一位
```

> 带剧本的特殊客人不按这个生命流程

### 3.2　随机客人的生成时序

```text
开始生成今天的名单
  ↓ 洗牌身份池，按位次取身份
  ↓ 容器（15% 特殊 / 85% 正常）→ 破洞数 → 破洞位置
  ↓ 自带物品
  ↓ 需求段
  ↓ 预算
  ↓ 生命值
  ↓ 组装 CustomerInstance
```

### 4.1　立绘与气泡

| 元素     | 规则                                                    |

### 4.3　离场

结算动画播完，停 1 秒，客人才带着箱子离开；柜台出现「下一位客人」按钮。

## 5　边界与异常

| #   | 情况                             | 期望行为                                                 |
| --- | -------------------------------- | -------------------------------------------------------- |
| 1   | 客人没有容器                     | 只显示立绘和气泡，不显示容器框，不能放货；谈完进"下一位" |
| 2   | 容器延迟上台                     | 容器已创建但不可交互，显示空台面（与"没有容器"不同）     |
| 3   | 剧本选项没答完就成交             | 拒绝；仍可继续装货                                       |
| 4   | 自带物品超过 60%                 | 生成期就不允许：最后一件不放，撤回并结束循环             |
| 5   | 需求点名的大件塞不进箱子         | 生成期换成同类别的小件或退化成类别需求                   |
| 6   | 需求总格数超过空位一半           | 先降件数到 1，再退化成类别需求                           |
| 7   | 预算低于最便宜的商品             | 允许成交，只收很少的钱（不做下限保护）                   |
| 8   | 选项要求的东西库存不够           | 选项不可点（`requires` 校验）                            |
| 9   | 同一天轮到两位剧本客人           | 由日程保证不冲突，S04 不处理                             |
| 10  | 客人离场时还有玩家的货在他箱子里 | 随客人一起离开，不返还（成交已经结算）                   |
| 11  | 声望到 0 或 100                  | 夹在边界；分别落在 0~24 与 75~100 档，按该档概率表出人数 |
| 12  | 客人数量超过身份池               | 身份按池子循环取用，允许重复                             |

## 6　验收用例

| #   | Given                | When                      | Then                                   |
| --- | -------------------- | ------------------------- | -------------------------------------- |
| 1   | 声望 0（0~24 档）    | 生成今日名单              | 人数只能是 2 或 3 位                   |
| 2   | 声望 100（75~100 档）| 生成今日名单              | 人数只能是 3、4 或 5 位                |
| 3   | 任意客人             | 命中特殊容器（15%）       | 尺寸 / 不可用格 / 预算 / 自带目标全按 2.2 表，不套公式 |
| 4   | 任意客人             | 检查容器尺寸              | 落在 6~10 之间                         |
| 5   | 任意客人             | 检查需求段数              | 1 或 2 段                              |
| 6   | 只有 1 段需求        | 检查类型                  | 不是点名需求                           |
| 7   | 有 2 段需求          | 检查类型                  | 至少一段不是点名                       |
| 8   | 点名需求             | 检查该物品                | 四个朝向里至少一个能塞进这个箱子       |
