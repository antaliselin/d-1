## 0　摘要

**这段要回答**：这个系统在整局里负责什么，不负责什么，谁依赖它。

### 0.1　一句话职责

把「箱子里装了什么」换算成「客人付多少钱」：**逐件定价 → 逐件从预算里扣 → 汇总**，并把这次成交的结果上报给 S04（声望）。

### 0.2　不做什么

| 不做                         | 谁做               |
| ---------------------------- | ------------------ |
| 不判断物品能不能放下         | S01 网格与容器     |
| 不改库存、不建实例、不算放置 | S02 物品与库存     |
| 不决定客人要什么、有多少钱   | S04 客人与特殊客人 |
| 不管拖拽手势                 | S03 拖拽与交互     |
| 不画飘字、不播动画           | 客户端表现         |

### 0.3　依赖

- 上游：S04（需求、预算）、S02（单价 `value`、弹药 `rounds`、枪内 `magRounds`/`loadedAmmoId`、协同字段 `connectItem_*`）、S01（可用格数）。
- 下游：S04（声望上报）、界面（飘字与预算牌）。

### 0.4　验收标准

一句话：**给一个装满的箱子，策划能手工算出与程序完全一致的金额。**

可测三条：

1. 任意箱子，手算金额与程序结果一致（误差 0）。
2. 实收金额永远 ≤ 客人预算。
3. 箱子空着时不能成交。

## 2　规则

**这段要回答**：一件货值多少、按什么顺序扣、扣到什么时候停。

### 2.1　参与结算的东西

```text
计入：
    玩家的货（owner = shop）——全部计入
    客人的枪里装着的子弹——单独作为一条商品计入（值是 弹.value × magRounds）
不计入：
    客人自带的其他物品——本身不卖钱，但它们的标签与 id 参与 2.4 的协同判定
```

### 2.2　单件实际价值 `V`

```text
普通物品        V = value
弹药            V = value × 剩余发数            // value 是「一发」价（S02 1.1）
枪（装了弹的）  V = value + 弹.value × magRounds
枪（空枪）      V = value
```

### 2.3　是否符合需求与底价 `base`

```text
符合需求 = 满足任一条：
    这件物品的 tags 与某个需求段的 tags 有交集
    这件物品在 wants 里被点名

base = 符合需求 ? V : round(V × UNRELATED_PAY_RATE)
```

- 只有两种结果：**符合 → 全额；不符合 → 半价**，没有中间档。
- 主段与次段的区别只体现在文案与优先级上，**不参与算钱**。
- 一件物品有多个标签时，只要命中任一段就算符合，不需要区分命中了几段。
- 客人的枪里装着的子弹，按子弹自己的标签判（不是按枪的）。

### 2.4　条件协同加成 `bonus`

完全按 S02 2.9 执行，这里只重复三个要点：

```text
gain = max(命中的 connectItem 声明值, 0)
cap  = round(base × CONNECT_BONUS_CAP_PCT / 100)
bonus = min(gain, cap)
```

- 只认声明方；搭档可以是客人自带的东西；存在性判定，不按件数叠。
- 自己的 id / 自己的标签不参与匹配（不会自我加成）。
- **base 为 0 的件不会拿到加成**（0 × 30% = 0）。

### 2.5　逐件扣预算（核心）

**不是"总价与预算取小"，而是一件一件扣。**

```text
remaining = budget
按顺序遍历 entries（顺序见 2.6）：
    payBase  = min(base,  remaining);  remaining -= payBase
    payBonus = min(bonus, remaining);  remaining -= payBonus
    记录 payBase / payBonus
    如果 remaining == 0：后面的件全部记 0，但仍要记账、仍要播飘字
price = Σ(payBase + payBonus)
```

- **先扣底价、再扣加成**：同一件里加成排在底价后面，底价扣光了加成也就没了。
- 被截断的件仍然算"卖了"，只是收不到钱；它照样占格、照样随客人离开。
- `budgetCapped = (price 的标价总额 > budget)`，只用于界面提示。

### 2.6　结算顺序

```text
先按容器里的行（y 从小到大）
再按列（x 从小到大）
同一格（理论上不会发生）按 instanceId 排
```

这个顺序**同时决定**：谁先拿到钱、飘字按什么顺序播。玩家把贵的放在左上角，就能优先拿到钱——这是设计的一部分，不要改成按价值排序。

### 2.7　治疗奖励

```text
healReward = 本次回复量 × HEAL_COIN_PER_HP
           + (这次治疗把客人治到满血 ? FULL_HEAL_BONUS : 0)
```

- 治疗奖励**不占客人预算**，与商品一起结算，但单独计入 `healReward`。
- 本次回复量由 S02 治疗时累加，S05 只读。
- 治疗奖励计入 `total`，也就是当日收入。

### 2.8　填充率

```text
fillBase   = 可用格数 − 客人自带物品占的格数
fillRatio  = 玩家物品占的格数 / fillBase
```

只用于界面展示与调试，**不参与定价、不影响声望**。

### 2.9　声望上报

成交后调用 S04 的声望接口，规则：

```text
对每一个需求段：
    箱内有这一段的物品，且这一件实际到账 > 0（没被预算截断） → 这一段记满足
每个满足的段：声望 +1

这次治疗把客人治到满血 → 声望 +1

箱内要计价的物品全部不符合需求，且箱内非空 → 声望 −2

结果夹在 0~100
```

- "满足"按**实际到账 > 0** 判：被预算截断到 0 的那段不算满足。
- 声望只有一个入口（S04 2.7），S05 只上报，不自己改数。

## 3　状态与流程

**这段要回答**：一次成交经历什么。

### 3.1　成交时序

```text
玩家点"成交"
   ↓ 判空：箱内没有可计价物品 → 拒绝（reason = empty）
   ↓ 判对白：选项没答完 → 拒绝（S04）
   ↓ 建 entries：玩家的货 + 客人枪里的子弹，按 2.6 排序
   ↓ 逐件算 V → 判是否符合需求 → base → bonus
   ↓ 逐件扣预算，生成飘字序列
   ↓ 播放结算动画（顺序 = 扣款顺序）
   ↓ 治疗奖励并入 total，入账
   ↓ 上报声望（S04）
   ↓ 客人道谢、带箱子离场 → 下一位
```

### 3.2　与其它系统的接口

| 本系统消费 | 来自 | 用途 |
| --- | --- | --- |
| `demand` / `wants` / `budget` | S04 | 定价与封顶 |
| `value` / `rounds` / `magRounds` / `loadedAmmoId` | S02 | 计算 V |
| `connectItem_*` | S02 | 协同加成 |
| 治疗回复量 / 是否回满 | S02 | 治疗奖励 |
| `placeableCount` | S01 | 填充率 |

| 本系统产出 | 给谁 | 用途 |
| --- | --- | --- |
| `Offer.entries` | 客户端 | 逐件飘字 |
| `price` / `total` | 经济与存档 | 入账 |
| 满足的段数 / 是否回满 / 是否全需求外 | S04 | 声望涨落 |

## 4　交互与表现

**这段要回答**：玩家怎么看到这笔账。

### 4.1　逐件飘字

| 元素 | 规则 |
| --- | --- |
| 顺序 | 严格按 2.6 的顺序，一件播完再播下一件 |
| 底价颜色 | **绿色** = 需求内全额；**白色** = 需求外半价 |
| 加成颜色 | 黄色，单独飘一次，跟在底价后面 |
| 金额 | 显示实际到账（被截断时显示截断后的数） |

### 4.2　预算牌

客人名字下方实时显示：`预算 $410 · 余 $275`。空箱时只显示 `预算 $410`。

### 4.3　收尾

最后一件飘完，停 **1 秒**，客人才离场；结算期间底部按钮显示「结算中…」，不能点下一位。

## 5　边界与异常

| # | 情况 | 期望行为 |
| --- | --- | --- |
| 1 | 箱子空着 | 不能成交，`reason = empty` |
| 2 | 箱内只有客人的东西 | 视同空箱（没有可计价物品），不能成交 |
| 3 | 全部不符合需求 | 可以成交，按半价结算；声望 −2 |
| 4 | 标价总额超过预算 | 按 2.5 逐件截断，最后一件可能只拿到零头 |
| 5 | 某件被截断到 0 | 仍算卖了、仍随客人离开；该段不算"满足" |
| 6 | 0 发弹药 | 不会出现（S02 规定减到 0 即销毁） |
| 7 | 客人自带枪里有玩家装的子弹 | 子弹单独作为一条商品计价，坐标跟随那把枪 |
| 8 | 点名要的东西没放 | 不影响成交，只是少了一段需求与对应的声望 |
| 9 | 治疗满血后才成交 | healReward 只按实际回复量算，满血治疗会被 S02 拒绝 |
| 10 | 一次治疗治满 | +FULL_HEAL_BONUS，并且声望 +1 |
| 11 | 预算刚好等于标价 | 全额支付，`budgetCapped = false` |
| 12 | 结算动画播放中被强制中断 | 金额已经算定，不重算；恢复后从断点继续播 |

## 6　验收用例

**手算算例**：6×6 箱子，客人主段 `ammo`、次段 `food`，预算 **100**。

| 顺序 | 物品 | V | 符合需求 | base | 已扣 | bonus | 余额 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 手枪弹盒（50 发 × 1） | 50 | 是 | 50 | 50 | 8 | 42 |
| 2 | 罐头 | 15 | 是 | 15 | 15 | 0 | 27 |
| 3 | 木板 | 20 | 否 | 10 | 10 | 0 | 17 |
| 4 | 旧式手枪（空枪） | 135 | 否 | 68 | **17** | 0 | 0 |

- 弹盒的 8 = `min(声明 8, round(50 × 30%) = 15)`，箱里有手枪（`pistol` 标签）所以命中。
- 第 4 件标价 68，但只剩 17，实际只收到 17；加成按 0 算。
- `price = 50 + 8 + 15 + 10 + 17 = 100`，正好等于预算，`budgetCapped = true`。
- 声望：`ammo` 段满足（+1）、`food` 段满足（+1），没有出现"全部不符合需求"，合计 +2。

| # | Given | When | Then |
| --- | --- | --- | --- |
| 1 | 上述箱子 | 结算 | `price = 100`，`total = 100` |
| 2 | 预算改成 500 | 结算 | 四件全额：50+8+15+10+68 = 151 |
| 3 | 箱内只放木板 | 结算 | 仍然可以成交，按半价收 10；声望 −2 |
| 4 | 箱内只有客人的枪 | 结算 | 不能成交（无可计价物品） |
| 5 | 箱内放空枪 + 弹盒，装 8 发 | 结算 | 枪 = 135 + 8 × 1 = 143，弹盒剩 42 发 = 42，合计 185（装弹只是把子弹从盒里搬到枪里，总额不变） |
| 6 | 箱内放弹盒，没有枪 | 结算 | 弹盒无加成，收 50 |
| 7 | 客人 hp = 60，用绷带回 35 | 结算 | `healReward = 35`，`total = price + 35` |
| 8 | 客人 hp = 60，用喷雾治满 | 结算 | `healReward = 40 + 50 = 90`，声望额外 +1 |
| 9 | 需求两段，只满足了一段 | 结算 | 声望 +1 |
| 10 | 一件货都没放，直接点成交 | 结算 | 拒绝，提示箱子空着 |
